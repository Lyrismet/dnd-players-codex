# Правила для всех версий

Действуют в каждой версии, поэтому не копируются в папки версий. Код и архитектура: `CLAUDE.md`. Каталог блоков
интерфейса:
`docs/CORE_COMPONENTS.md`. Что приложение умеет сейчас: `docs/FEATURES.md`.

## Готовность задачи (для каждой задачи без исключений)

1. Код по слоям `CLAUDE.md`: Presenter, Ui, Screen, Circuit-фабрика, домен без фреймворков, `data` за интерфейсом.
2. Любое изменение схемы - `.sqm` с `DEFAULT` или backfill и тест миграции на старой версии. Старые данные живут.
3. Все строки в `values` и `values-en`, плюрали через `<plurals>`, словарь проекта. Нового хардкода текста нет.
4. Новый визуальный блок сначала ищется в `docs/CORE_COMPONENTS.md`; новый примитив добавляется туда же в том же PR.
   Новый
   общий пакет презентации добавляется в `SHARED_PRESENTATION` (`ArchitectureTest`).
5. Чистая логика под `core/*` и `feature/*/domain` с тестом в `commonTest`. Имена тестов в обратных кавычках без запятых
   и
   точек (Kotlin/Native).
6. Архив только для чтения: новые кнопки скрыты и отсекаются в презентере.
7. Проверка: `./gradlew build -x :shared:linkReleaseFrameworkIosArm64 -x :shared:linkReleaseFrameworkIosSimulatorArm64`,
   `./gradlew ktlintFormat`, `./gradlew detekt`. Устройство проверяет владелец, агенты эмулятор не запускают.
8. Пункты `docs/FEATURES.md` и шаг в `README.md` версии отмечаются `[x]`, когда работа сделана и проверка (сборка,
   `ktlintFormat`, `detekt`, тесты) зелёная, не ждём приёмки на устройстве: отметка честно говорит, что код готов. Если
   владелец потом просит поправить с отклонением от первоначального функционала, формулировка пункта меняется под
   фактическое поведение (в `docs/FEATURES.md` и в документе версии). Что проверить на устройстве, агент
   перечисляет в отчёте.

## Сквозные правила продукта

- Кодекс не меняется молча: всё, что приложение вычислило само (из заметки, из отдыха, из файла), применяется только
  после нажатия игрока и с Undo.
- Архивная кампания только для чтения: новые кнопки и правки скрыты и отсекаются в презентерах (`CodexReadOnly`,
  `SessionDetailReadOnly`).
- **Схема БД меняется только с миграцией** (`.sqm` и тест на старой версии, см. `CLAUDE.md`). У тестеров живые данные.
- Правила системы живут в одном заменяемом месте. Сейчас это шаблон D&D 5e по SRD 5.1 (формулы листа персонажа), класс и
  тип восстановления ресурса приложение само не выводит, их вводит игрок. Любую числовую плитку можно заполнить просто
  числом. Пресеты других систем в бэклоге.
- Термин "хиты" везде, не "HP". Пустое значение - серый прочерк "—".
- Крупные числа (хиты, бонусы, кошелёк, степперы) набираются шрифтом Inter, не засечным: ноль не должен походить на "О".
- Окно Undo остаётся 5 секунд (`UNDO_WINDOW_MILLIS` в `core/undo`).
- Метка своего персонажа "я", обращения к игроку на "вы". Тексты без угадывания пола людей и персонажей.

## Очередь шагов

- Шаги берутся **по порядку**. Шаг не начинается, пока предыдущий не слит и не отмечен `[x]` в `README.md` версии. Если
  шаг
  застрял, можно брать следующий, не зависящий от него (колонка "Зависит от").
- **Имя ветки:** `s<N>_<кратко_о_фиче>`, где `N` номер шага, дальше 1-3 слова латиницей в нижнем регистре через `_`, без
  дефисов и кириллицы (`s7_import_merge`). Ветка создаётся от свежего `master`.
- Один шаг, один PR, один заход агента. Не склеивать шаги и не подтягивать задачи из соседних.
- **Не коммитить** (`git commit` запрещён, только готовить и стейджить). Коммитит владелец.
- Номера миграций в брифах ориентировочные: агент сверяет их с `shared/src/commonMain/sqldelight/migrations/` в начале
  шага.
- Ссылаться на другие документы по заголовку раздела, а не по номерам строк: строки уезжают при первой правке.
